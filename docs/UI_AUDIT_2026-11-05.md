# Desktop and laptop UI audit — 2026-11-05

## Verdict

The storefront has a coherent technical-apparel visual identity and a sensible application structure. It is a good portfolio foundation. It needs a targeted readability and accessibility pass before it should be described as broadly accessible or fully user-ready. A redesign or framework replacement is unnecessary.

This was an inspection, not an implementation. No application source, catalog records or configuration were changed.

## Scope and evidence

- Inspected the running local storefront and source CSS, shared layout, homepage, product cards, document shell, routes, request/controller/service organization and test setup.
- Measured homepage geometry and computed typography at 1280, 1366, 1440 and 1920 CSS pixels; additionally checked 1024px navigation and a 683px compact reflow viewport. Desktop heights included 768px and 900px.
- Visually reviewed laptop homepage, desktop shop and product details. Inspected contact form and About page typography and semantics at 1440px.
- No horizontal document overflow in the inspected layouts. Homepage hero/editorial copy stayed within its containing section at the measured widths.
- Keyboard Tab exposed the skip link with a visible blue outline; Enter moved focus to main.
- TypeScript `npm run types:check`: passed. Existing React tests: 16 passed across two files.
- This review did not rerun backend or full cross-browser suites, test populated bag/checkout/staff pages, perform a complete screen-reader evaluation, measure field Core Web Vitals, or certify WCAG conformance. Compact-width reflow is not a substitute for a complete actual-browser zoom/text-resizing test.

## Prioritized findings

### 1. Increase functional text sizes — high usability priority

The desktop interface gives large images and headings much more visual weight than the controls people use. The buttons themselves have comfortable heights, but their labels are small. Smaller laptops also shrink navigation through viewport-based type sizing.

| Element | Measured current value | Recommended target |
| --- | --- | --- |
| Homepage, filter, product and contact button labels | 11px | 14–16px |
| Main navigation | 12.8px at 1280; 13.66px at 1366; 14px at 1440+; 10.24px at 1024 | Stable 14–16px; adapt spacing or navigation layout before shrinking text |
| Shop filter values | 13px | 16px |
| Price From/To values and labels | 12px | Values 16px; labels 14px |
| Product description | 14px / 25.2px line height | 16px with comfortable line height |
| Product size/status labels | 12px | 14px |
| Contact labels | 12px | 14px; preserve existing 16px field text |
| Product card name and price | 15px | Acceptable; 16px would improve consistency |
| Footer | 13px | 14px |
| View All / pagination | 12px | 14px |
| About paragraphs | 15px / 28.5px line height, 804px content width | 16–18px, approximately 60–75 characters per line |
| Homepage heading at 1366 | 50.542px | Appropriate for its role; keep |
| Homepage description at 1366 | 20.49px | Appropriate; keep |

These size targets are usability recommendations, not a claim that WCAG mandates a universal 16px minimum. WCAG instead addresses properties including contrast, resizing, reflow and operability. Small secondary metadata can remain smaller where legible; primary actions deserve stronger treatment.

Locations: `resources/css/app.css:33`, `:53`, `:101`, `:161`, `:165`, `:170`, `:202`, `:219`, `:239`. The existing mobile overrides already improve several controls, so desktop currently receives smaller text than phones.

### 2. Darken muted text on the page background — accessibility issue

The palette uses muted `#68737D` on page background `#F5F6F6`. Their calculated contrast is approximately **4.47:1**, slightly below the **4.5:1** requirement for normal text. This affects uses such as current breadcrumbs, shop secondary text and the product demo note. The same gray on white is approximately **4.84:1**, which passes that text threshold.

Darken the shared muted token enough to provide margin above the threshold, then check its actual surfaces. Do not round 4.47 up to a passing value. White text on the cobalt button background `#145DFF` is approximately **5.20:1** and is already sufficient for normal text.

Locations: `resources/css/app.css:12`, `:171`, `:183`, `:219`.

### 3. Strengthen form-field boundaries — high accessibility priority

The field border `#DDE2E6` has approximately **1.21:1** contrast against the page background and **1.30:1** against its white interior. White field fill against the page background is approximately **1.08:1**. The search, price and contact fields therefore have weak visible boundaries.

Where the boundary is needed to identify the editable area, provide a border or another sufficient cue with at least **3:1** contrast against the adjacent background. Retain distinct, high-contrast focus and error states. This requirement does not mean every decorative divider must be darkened, nor does every labeled control automatically fail solely because its border is faint; blank text-entry regions are the clearest problem here.

Locations: shared `input, select, textarea` rule and `.form-field input` in `resources/css/app.css`.

### 4. Give the main navigation an active state — medium usability priority

On `/shop`, the desktop primary navigation has no `aria-current` or visible current-section indication. Breadcrumbs help, but adding an underline/weight treatment and an appropriate current state makes location easier to understand. Avoid color as the only indicator. Define how collection and product pages relate to the Shop section.

Location: `resources/js/layouts/store-layout.tsx:33`.

### 5. Consolidate style rules and tokens — maintenance priority

The application structure is reasonable: Laravel models, validated requests, controllers, middleware and services; React pages, shared layouts and reusable components; strict TypeScript; locked dependencies; SSR and responsive image handling; backend, component and browser tests.

The main maintainability weakness is the stylesheet: repeated selector overrides, several separate media blocks for the same breakpoint, and many individually specified pixel sizes. Introduce a compact typography/spacing token scale and consolidate related component rules. Express ordinary typography in rem where useful, and verify user font preferences and zoom. CSS pixels alone are not automatically a WCAG failure.

The responsive behavior document also contains multiple superseded historical instructions. A concise current contract separated from the change history would reduce future regressions.

No Git commits currently exist and project files are untracked. This does not affect rendering, but means the present changes have no committed recovery baseline. Create a reviewed baseline and backup before larger refinements; do not include environment secrets or generated dependencies. No commit was made during this inspection.

## Strengths to preserve

- Consistent palette, original imagery, clear identity, image-backed editorial composition and readable large headings.
- Responsive grids and maximum-width content rather than uncontrolled stretching on wide monitors.
- Typical header/form/quantity targets of at least 44px; card swatch targets measured 28×28px, exceeding WCAG 2.2's 24×24px size minimum. Larger swatches would still be easier to use.
- Semantic page headings, named navigation regions, labeled contact fields, image alternatives and a working skip link.
- Explicit reduced-motion CSS, focus-visible treatment and native-dialog navigation focus management in source.
- Contact inputs already use 16px text; product card text is reasonably sized.
- SSR, lazy loading below the hero and responsive image sources are sound foundations, though performance scores were not measured here.

## Recommended acceptance checks after refinement

1. Repeat desktop checks at 1024, 1280, 1366, 1440 and 1920px, including a 1366×768 laptop viewport.
2. Check actual browser zoom at 200%, narrow reflow, text spacing and user font preferences without clipped text or inaccessible controls.
3. Verify text and meaningful control contrast, including text over both campaign images at all relevant crops.
4. Walk keyboard navigation through header, search, filters, swatches, sizes, bag and checkout; verify visible focus and that the sticky header does not obscure it.
5. Rerun the existing TypeScript/component/responsive suites after CSS changes, and inspect screenshots rather than relying only on test counts.
